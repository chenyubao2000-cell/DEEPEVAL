A. 运行健康 / Ops（8 件套，全部在用）

这一组属于 custom_metrics/，是从旧 Mira_Validation 移植 + 项目内自建的运营信号。 评分多为原始数值（tokens / USD / 秒），不是 0-1，靠 BaseValueMetric.informational 切换 gate 或 info-only 行为。 8 个里 7 个是确定性查询（Langfuse/PG），仅 ToolDependencyMetric 调 LLM judge。
指标 优先级 状态 评分原理 / 适用场景 出处
SessionHealthMetric ★ P0 核心 ● 在用 (gate, =1.0) 统一的"session 是否完成干净"门禁，三层独立检查全跑（不短路）：
  • client — 内存 MiraSession 信号：stream_truncated 警告 / 工具 status==error / 空 assistant turn（旧 RunCompletionMetric 的逻辑）。无网络调用。
  • trace — Langfuse trace：至少 1 个 trace 有 end_time 或 mira-agent observation 完成；level == DEFAULT；最后 assistant turn 内容非空（旧 CompletedMetric 的逻辑）。
  • persistence — Mira Postgres messages 表：user/assistant 严格成对；每条 assistant parts[-1] 处于合法终止态；所有 part 状态合规（旧 DatabaseStatusMetric 的逻辑）。metadata.aborted=true 跳过。
score 是 binary 1.0/0.0：所有非 skipped 层都 pass 才 1.0。.reason 是多行结构化诊断（每层一行 ✓/✗/🚨/•），方便报告里一眼看出"挂在哪一层"。 Langfuse / PG 拿不到 → 该层 status="error"（报告高亮 🚨）+ 总分 FAIL（"无法验证"也算不过）。 用途：执行层 + observability 层 + 持久化层三道防线一次过；当此 metric fail 时，下游所有 quality metric 都不可信。 		custom_metrics/status_metrics.py
test_mira_ops.py
NTurnsMetric P0 核心 ● 在用 (gate, ≤30) 统计最后一次 doStream observation 的 input.messages 里 role==user 的条数，越界即 fail。 用途：防 Mira 进入 runaway 对话循环（曾因 tool retry 把上下文打到 100+ turns）。 custom_metrics/perf_metrics.py
test_mira_ops.py
ToolDependencyMetric P0 核心 ● 在用 (gate, ≥0.80) 抽出工具调用序列 → 加载 tool-dependencies.json 的约束 catalog → claude CLI 判 violation → score = (totalSteps − violatingSteps) / totalSteps。0 tool call 或 0 violation 直接 1.0（lenient）。 用途：检查工具调用是否违反业务约束（例如 "先 search 再 send_email"），唯一一个调 LLM 的 ops 指标。 custom_metrics/path_metrics.py
test_mira_ops.py
TokensMetric P1 重要 ● 在用 (info-only) 跨 session 累加 trace.usage 的 input+output。 用途：token 趋势监控；曾因 CRM 用例普遍 1M+ tokens 导致硬阈值假阳，已改 informational。 custom_metrics/usage_metrics.py
test_mira_ops.py
SessionCostMetric P1 重要 ● 在用 (info-only) 4 段优先级回退取 USD：totalCost → calculatedTotalCost → cost → observations 累加。 用途：单 session 成本飘动监控，配合 token 数一起看。 custom_metrics/usage_metrics.py
test_mira_ops.py
TimeToFirstTokenMetric P1 重要 ● 在用 (info-only) 跨 LLM generation 取 min(timeToFirstToken)。 用途：首 token 延迟监控，前端体感受其直接影响。 custom_metrics/perf_metrics.py
test_mira_ops.py
SessionDurationMetric P1 重要 ● 在用 (info-only) 跨 trace + observations max(endTime) − min(startTime)，墙钟时长。 用途：整个 session 的端到端耗时，便于回归。 custom_metrics/perf_metrics.py
test_mira_ops.py
OutputTokensPerSecMetric P1 重要 ● 在用 (info-only) Σ output_tokens / duration，唯一 higher_is_better=True 的 Ops 指标。 用途：流式吞吐率，模型/上游切换时回归对比。 custom_metrics/perf_metrics.py
test_mira_ops.py

B. 单轮内容质量 — 在用

指标 优先级 状态 评分原理 / 适用场景 出处
AnswerRelevancyMetric P0 核心 ● 在用 (gate, ≥0.5) 把 actual_output 拆 statement，逐条判是否回应 input，"相关数 / 总数"。 用途：单轮"答非所问"筛查，最基础的内容相关性指标。 test_mira_others.py
PromptAlignmentMetric P1 重要 ● 在用 (gate, ≥0.7) 逐条 prompt_instructions 检查 actual_output 是否遵守，符合占比。Mira 注册了 5 条人工蒸馏指令（专业语气、不瞎编、要交付物等）。 用途：把系统提示词关键约束转成可量化检查，绕开"读不到真实 system prompt"的限制。 test_mira_others.py

C. 多轮对话质量 — 在用

Mira 的多轮场景由 ConversationalTestCase(turns=[Turn(role,content,...)]) 驱动； 这一组指标全部基于 BaseConversationalMetric，是当前评测的主力。
指标 优先级 状态 评分原理 / 适用场景 出处
GoalAccuracyMetric P0 核心 ● 在用 (gate, ≥0.5) 多轮综合：目标是否达成 + plan 分，求平均。读 scenario / expected_outcome。 用途：整段对话是否完成用户目标，最贴近用户体感。 test_mira.py / test_mira_e2e.py
RoleAdherenceMetric P0 核心 ● 在用 (gate, ≥0.7) 检测 assistant 是否符合 chatbot_role 人设（"Mira, a professional workplace AI agent."）。 用途：多轮人设是否稳定，避免漂出"招聘助理"定位。 test_mira.py / test_mira_e2e.py
ConversationCompletenessMetric P1 重要 ● 在用 (gate, ≥0.5) 抽用户意图清单 → 判对话是否每条意图都被满足。window_size=3。 用途：用户多个诉求是否一个都没漏。 test_mira.py / test_mira_e2e.py
TurnRelevancyMetric P1 重要 ● 在用 (gate, ≥0.5) 滑窗判每个 assistant turn 与上下文的相关性。window_size=10。 用途：每一轮是否切题，对长对话比 AnswerRelevancy 更合适。 test_mira_e2e.py
KnowledgeRetentionMetric P1 重要 ● 在用 (gate, ≥0.5) 逐 turn 检查 assistant 是否记住前文用户给的信息（公司名、JD 要求、人选偏好等）。 用途：长对话记忆稳定性，是 Mira 当前已知短板的核心信号。 test_mira_e2e.py
TopicAdherenceMetric P1 重要 ● 在用 (gate, ≥0.5) TP/TN/FP/FN 混淆矩阵判对话是否偏离预设主题。Mira 注册了 10 个 topic（招聘、市场研究、文档生成、CRM、voice、email、calendar 等）。 用途：跨业务 category（CRM / voice / ci_email / ci_dingding）防主题跑偏，2026-05-11 扩充 topics 后修正了 false-negative。 test_mira_tooluse.py

D. 安全合规 — 在用

指标 优先级 状态 评分原理 / 适用场景 出处
PIILeakageMetric P0 核心 ● 在用 (gate, ≥0.7) 检测响应是否含个人身份信息（姓名/手机/身份证/邮箱等）。 用途：招聘场景 PII 极敏感，候选人/客户隐私必须把关。 test_mira_safety.py
RoleViolationMetric P0 核心 ● 在用 (gate, ≥0.7) 二值打分：偏离 role 即 0。当前 role = "Mira, a professional workplace AI agent."。 用途：单轮角色硬检测，与 RoleAdherence（多轮）互补。 test_mira_safety.py
BiasMetric P1 重要 ● 在用 (gate, ≥0.7) 抽 actual_output 中观点，判是否含性别/种族/政治倾向偏见，偏见比例越低分越高。 用途：招聘场景下歧视风险高发，必须监控。 test_mira_safety.py
ToxicityMetric P1 重要 ● 在用 (gate, ≥0.7) 同 Bias 结构，判是否含有毒 / 仇恨 / 骚扰内容。 用途：兜底有害内容筛查。 test_mira_safety.py

E. 工具调用 — 在用

指标 优先级 状态 评分原理 / 适用场景 出处
ToolUseMetric P0 核心 ● 在用 (gate, ≥0.5) 多轮版：每个 user-assistant 交互判工具选择 + 参数正确性，取最小。available_tools 从 Langfuse 缓存动态注入。 用途：Mira 多轮链路的工具调用整体质量，是工具类指标的主力。 test_mira_tooluse.py
ArgumentCorrectnessMetric P0 核心 ● 在用 (gate, ≥0.5) 单轮逐 tool call 判参数是否符合 input 语义，正确占比。 用途：检测工具入参对不对，无需 ground truth；和 ToolUse 互补，一个看选择一个看参数。 test_mira_tooluse.py

F. 自定义维度 ConversationalGEval — 在用

ConversationalGEval 是当前自定义评测的主力武器：业务想测什么，写 criteria/evaluation_steps， 指定 evaluation_params（必须在 CONVERSATIONAL_G_EVAL_PARAMS 允许的 8 个 key 内）。
实例 优先级 状态 评分原理 / 用途 出处
ConversationalGEval
(ProfessionalNoFabrication)		 P0 核心 ● 在用 (≥0.7) 专业语气 + 不瞎编 + 不暴露 LLM 内部机制（如"我没有跨会话记忆"）+ 用户含糊时主动追问。 用途：工作场景下的人设 + 反幻觉，是 Mira 区别于通用 chatbot 的核心维度。 test_mira.py / test_mira_custom.py
ConversationalGEval
(DeliverableMatchesRequest)		 P0 核心 ● 在用 (≥0.6) 判用户提到的每一个可交付物（PPT/Excel/PDF/图片/N 人候选清单/分析报告）是否真被产出。仅口头描述算中分；忽略或替换无关内容低分；无法访问数据源时必须显式说明。 用途：Mira 是"产出导向"的 agent，最容易出"光说不练"问题。 test_mira.py / test_mira_custom.py
ConversationalGEval
(GroundedNoFabrication)		 P0 核心 ● 在用 (≥0.6) 每条事实声明（公司名/人名/统计数据/薪资/URL/日期/市场规模）必须有引用 OR 显式数据局限声明。模糊通用建议可；自信地编造具体数字 → 低分。 用途：把"反幻觉"做成可量化指标，比 PromptAlignment 里的"不要瞎编"细得多。 test_mira_custom.py

G. RAG 检索质量 — 未启用（缺 retrieval_context）

这一族全部需要 retrieval_context 字段（或多轮版的 turns[*].retrieval_context）。 Mira 目前 TS 后端没把检索结果（向量库片段、知识库匹配）通过 SSE/API 透出来。 启用前置工作：在 Mira BFF 流式协议里加 retrieval 事件，_driver.py 解析后塞到 Turn 上。
指标 优先级 状态 评分原理 / 用途 缺什么
FaithfulnessMetric P1 重要 ○ 未启用 从 retrieval_context 抽 truths，从 actual_output 抽 claims，逐条判 claim 是否被 truth 支持。 用途：RAG 链路最重要的反幻觉指标，等检索结果暴露后强烈建议启用。 retrieval_context
ContextualRecallMetric P2 可选 ○ 未启用 把 expected_output 拆句，判每句是否被 retrieval_context 支持。
用途：检索是否覆盖理想答案。		 retrieval_context, expected_output
ContextualRelevancyMetric P2 可选 ○ 未启用 对每段 retrieval_context，判其内容是否与 input 相关。
用途：检索结果与查询的相关性。		 retrieval_context
ContextualPrecisionMetric P2 可选 ○ 未启用 加权精确率@k：top-k 中支持 expected_output 的密度。
用途：检索排序质量。		 retrieval_context, expected_output
TurnFaithfulnessMetric P2 可选 ○ 未启用 多轮版 Faithfulness。
用途：长对话 RAG 忠实度。		 turns[*].retrieval_context
TurnContextualRecallMetric P2 可选 ○ 未启用 多轮版 ContextualRecall。 turns[*].retrieval_context
TurnContextualRelevancyMetric P2 可选 ○ 未启用 多轮版 ContextualRelevancy。 turns[*].retrieval_context
TurnContextualPrecisionMetric P2 可选 ○ 未启用 多轮版 ContextualPrecision。 turns[*].retrieval_context

H. 内容质量补充指标 — 未启用

指标 优先级 状态 评分原理 / 用途 备注

这 4 个指标都标记 requires_trace=True，必须在 Python 侧用 @observe 构建 trace 树。 Mira 是 TS 后端，Python 端没有原生 trace —— 除非像 test_smoke_hello_observed.py 那样人工搭 span，否则用不了。
指标 优先级 状态 评分原理 / 用途 备注
TaskCompletionMetric P3 不适用 ✕ 需 @observe trace 从 trace 抽 task & outcome，判任务是否完成。
效果与 GoalAccuracy 重叠，本仓已用后者替代。		 requires_trace=True
PlanAdherenceMetric P3 不适用 ✕ 需 @observe trace 实际行动是否遵守计划。 requires_trace=True
PlanQualityMetric P3 不适用 ✕ 需 @observe trace 生成的计划本身是否完整 / 清晰 / 合理。 requires_trace=True
StepEfficiencyMetric P3 不适用 ✕ 需 @observe trace 步骤数与资源消耗是否高效。
本仓 OutputTokensPerSec + NTurns + SessionDuration 已经从结果端覆盖类似信号。		 requires_trace=True

建议下一步动作（按收益排序）

序号 优先级 动作 说明
1 P1 启用 MisuseMetric(domain="hiring assistant") 零业务改动，加一个字符串即可上线，把"招聘边界外的请求"做成硬约束。
2 P1 把 BFF 检索结果通过 SSE 透出，开 FaithfulnessMetric RAG 反幻觉的标准指标。需要后端配合在流里加 retrieval 事件。
3 P1 把 5 个 info-only Ops 指标里至少 SessionCost 升级为软门禁 例如设 threshold=2.0 USD 仅在超阈值时高亮，不直接 fail。当前完全只看趋势容易被慢慢飘高吃掉。
